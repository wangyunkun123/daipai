# 风格匹配路由 v2.0

## 核心设计哲学

**v1.0 的问题**：19 行静态匹配规则 → 匹配不到走兜底 → 用户无感。"兜底"的意思是"我不知道最好的答案，给你一个不出错的答案"。不出错的答案永远不会让用户兴奋。

**v2.0 的原则**：

```
规则不是引擎，是护栏。
AI 不是兜底，是引擎。
知识库不是真理，是缓存。
兜底不存在——每次都是一次发现。
```

---

## 一、新架构

```
┌─────────────────────────────────────────────────────────────┐
│                    🧠 AI 引擎层（主导）                        │
│                                                              │
│  场景输入 → AI 理解场景独特美学潜力                            │
│          → AI 搜索全球最佳风格匹配                             │
│          → AI 生成创意方案                                    │
│          → AI 发现知识空白并主动填补                           │
│                                                              │
│                    ↓ 约束传入                                 │
│                                                              │
│  🛡️ 规则护栏层（约束，不驱动）                                 │
│  ├─ 光线物理约束：顺光拍不了逆光通透                            │
│  ├─ 设备硬约束：没长焦拍不了空间压缩                            │
│  └─ 安全边界：不推荐危险机位                                    │
│                                                              │
│                    ↓ 结果沉淀                                 │
│                                                              │
│  📚 知识缓存层（加速，不限制）                                  │
│  ├─ 已有风格 → 快速通道（已验证 N 次）                         │
│  ├─ 新发现风格 → 自动注册（标记 discovered）                   │
│  └─ 验证计数 → 越多验证越优先推荐                              │
└─────────────────────────────────────────────────────────────┘
```

## 二、匹配流程

### 完整流程（4 步）

```
Step 1: 规则护栏 — 硬过滤
  ├─ 光线路由器 → 排除物理不可行的风格
  ├─ 设备约束   → 排除设备做不到的方案
  └─ 输出：安全候选池（排除名单 + 原因）

Step 2: AI 搜索发现 — 主匹配 🆕
  ├─ 场景美学提炼：一句话描述这个场景最动人的潜质
  ├─ 多源搜索：
  │   ├─ WebSearch × 3-5："{场景描述} photography style best lighting composition"
  │   ├─ WebSearch × 2："{场景描述} 摄影 风格 拍摄技巧"
  │   └─ WebSearch × 1："{类似场景} {类似光线} photographer reference"
  ├─ AI 综合判断：基于搜索结果 + 场景洞察，推荐 3-5 个最佳风格方向
  └─ 每个推荐附带：为什么适合 / 参考作品 / 可执行性评估

Step 3: 知识库对比
  ├─ AI 推荐 ∩ 知识库已有风格 → ✅ 直接使用（快速通道）
  │   标记验证计数 +1，增强未来匹配权重
  ├─ AI 推荐 - 知识库已有风格 → 🆕 新发现！
  │   ├─ 质量评估通过 → 采纳推荐，标记为"新风格候选"
  │   ├─ 触发轻量采集（见 §五）
  │   └─ 质量不足 → 降级为知识库已有次优匹配
  └─ AI 推荐包含已有风格的变体 → 🔄 变体发现
      标记为已有风格的 sub-type，记录触发场景

Step 4: 输出匹配结果
  ├─ primary: 最佳匹配 + 为什么
  ├─ alternatives: 2-3 个备选方向
  ├─ discoveries: 新发现（如有）
  └─ excluded: 排除的风格 + 排除原因（光线/设备/审美冲突）
```

### 关键变化：兜底逻辑废除

```
v1.0：
  题材+光线+情绪组合不在表中 → 参照最接近行 → 标记"风格手动匹配"
  结果：用户看到一个"还行"的推荐，没有惊喜

v2.0：
  场景不在知识缓存中 → AI 主动搜索发现 →
  ├─ 找到了更好的匹配 → 给用户惊喜 + 入库
  └─ 确认知识库中的最佳匹配仍然是全局最佳 → 给用户解释为什么
  结果：用户要么得到惊喜，要么得到"这个确实最适合你"的确定性
```

以下匹配表**不是真理，是经过验证的历史最佳实践**。它的作用是：

1. **加速**：已验证的匹配直接使用，不需要每次都搜索
2. **验证**：每条匹配记录验证次数，高验证=高置信度
3. **可更新**：AI 发现更好的匹配时，更新此表

### 3.3 缓存命中 vs AI 发现

```
缓存命中（该组合在上表中存在，验证≥2）：
  → 作为候选之一参与 AI 综合判断
  → AI 仍会搜索确认是否还有更好的
  → 如果 AI 确认缓存仍然最优 → 直接使用，不做无效搜索
  → 如果 AI 发现更好的 → 更新缓存

缓存缺失（该组合不在上表中）：
  → 不意味着"没有匹配"——意味着"还没探索过"
  → AI 全力搜索发现
  → 找到后自动注册到缓存表
  → 下一个人来秒出

缓存存在但验证=1（新注册）：
  → 正常使用，但 AI 会特别关注搜索结果是否支持或挑战这个新条目
  → 如果搜索结果一致 → 验证+1，置信度提升
  → 如果搜索结果不一致 → 标记 contested，积累更多验证
```

## 四、AI 搜索发现指南

### 4.1 搜索触发条件

以下任一情况，AI 执行搜索发现：

| 条件 | 触发 | 搜索深度 |
|------|:--:|------|
| 场景组合不在缓存表中 | ✅ | 深度搜索（5-7 次 WebSearch） |
| 缓存命中但验证 < 2 | ✅ | 中度搜索（3-4 次 WebSearch，验证为准） |
| 缓存命中且验证 ≥ 3 | 🚫 跳过搜索 | 直接使用缓存（除非用户要求探索） |
| 用户选择"✨ 脑洞大开" | ✅ | 广度搜索（不限于可执行性，搜创意） |
| 用户切换题材 | ✅ | 中度搜索（新题材的匹配关系） |

### 4.2 搜索策略

```
搜索模板（按顺序，可并行）：

#1: "{场景一句话描述} {光线特征} photography style inspiration"
    → 目标：全球范围内的风格参考

#2: "{题材} {光线条件} {情绪氛围} 摄影 风格 怎么拍"
    → 目标：中文社区的实际拍摄经验

#3: "{类似场景} photographer portfolio reference"
    → 目标：找到拍过类似场景的摄影师

#4: "{场景关键词} {风格候选1} {风格候选2} which style works best"
    → 目标：风格对比和选择依据

#5 (如适用): "{场景} {设备类型} photography technique"
    → 目标：设备特定的技法参考
```

### 4.3 AI 综合判断框架

搜索完成后，AI 综合判断输出：

## 五、自动知识沉淀 🆕

### 5.1 发现驱动的采集

v1.0：知识空白 → 兜底 → 用户无感 → 永远不补
v2.0：知识空白 → AI 搜索 → 找到答案 → 自动入库 → 下次秒出

```
每次方案生成都是一次知识发现机会：

方案生成完毕 →
  ├─ 检查方案中使用的风格匹配关系
  │   ├─ 在 style-router 缓存表中？ → 验证计数 +1
  │   └─ 不在缓存表中？ → 🆕 自动注册
  │
  ├─ 检查方案中产生的风格变体
  │   ├─ 如"清冷森系"是从"森系"变体而来
  │   ├─ 变体参数已在方案中明确（色温-15/绿色往青调等）
  │   └─ → 🆕 自动注册为风格变体
  │
  ├─ 检查方案中引用的大师视角
  │   ├─ 如"川内伦子 × 河边人像"这个组合
  │   └─ → 🆕 注册到 master-router 的场景匹配
  │
  └─ 输出变更摘要（静默，不打断用户体验）
```

### 5.2 轻量采集 vs 完整采集

| | 轻量采集（自动） | 完整采集（手动 /zhichu-collect） |
|---|---|---|
| 触发 | 方案生成时自动 | 用户主动调用 |
| 搜索 | 利用方案生成时的搜索结果 | 全新 Phase 1 多源搜索 |
| 参数提取 | AI 从方案中提取 | 完整 Phase 2 结构化分析 |
| 注册 | 写入缓存表 + 标记 `discovered` | 完整 Phase 4 全文件注册 |
| 置信度 | medium（需后续验证） | high（经过完整流程） |
| 用户感知 | 无感知（后台自动） | 有感知（输出变更摘要） |

### 5.3 自动注册到缓存表的格式

轻量采集写入 style-router 缓存表：

```markdown
| {题材} | {光线} | {情绪} | → {主风格} | → {变体风格} | → {破格方案} | 1 🆕 |
```

同时在风格源文件中追加一条 `discovered_from` 记录：

```markdown
<!-- discovered: 2026-07-23 | scene: "百善镇河畔+人像+户外软光+温暖松弛" | confidence: medium -->
```

## 六、风格冲突处理

| 冲突 | 处理 | 优先级 |
|------|------|:--:|
| 光线物理不可行 | **硬排除**——顺光拍不了逆光通透。不需要 AI 判断 | 最高 |
| 设备硬约束 | **硬排除**——没长焦拍不了空间压缩。不需要 AI 判断 | 最高 |
| AI 推荐与缓存不一致 | **AI 优先**——缓存是历史，AI 搜索是现在。但标记差异供后续验证 | AI > 缓存 |
| AI 推荐存在争议（搜索结果不一） | 标记 `contested`，同时呈现多个方向让用户选 | — |
| 审美冲突（如暖情绪+冷色调推荐） | **不排除**——冷色调+暖情绪可以是复合情绪的高级表达 | 最低 |
