# 带拍 · 产品架构规划

**日期**: 2026-07-24 | **当前阶段**: Skill 原型验证 | **目标**: 摄影知识引擎产品化

---

## 一、当前状态

daipai 目前是一个 Claude Code skill，所有逻辑通过 `SKILL.md`（自然语言指令）+ 4 个 Python 脚本 + 知识库 Markdown 文件运行。

```
当前架构：
  用户 ─→ SKILL.md（1743行，自然语言状态机）
              ├─ 调用 Python 脚本（exif/sun/reverse-geocode/light-schedule）
              ├─ 调用豆包视觉 API（识图）
              ├─ 调用 WebSearch（风格搜索 + 技法搜索）
              ├─ LLM 读写 Markdown 缓存表（知识沉淀）
              └─ LLM 生成方案文本
```

**Skill 的价值**：用自然语言快速验证核心想法，改文档就能迭代，不需要写代码。

**Skill 的边界**：当缓存表超过 ~50 行、调用量超过 ~100 次时，LLM 做精确操作（查表计分、编辑文件、计数+1）的可靠性开始下降。

## 二、核心原则：三条分界线

### 分界线 1：确定性的 → 代码

> **同样输入永远产生同样输出 → Python 脚本。**

| 工作 | 确定性 | 当前实现 | 产品实现 |
|------|:--:|------|------|
| EXIF 提取 | ✅ | Python ✅ | Python ✅ |
| 太阳位置计算 | ✅ 数学 | Python ✅ | Python ✅ |
| 天气查询 | ✅ API 调用 | curl 命令 | Python `weather.py` |
| 地点反向编码 | ✅ API 调用 | Python ✅ | Python ✅（+ 本地缓存） |
| 方向分配（标注→桶） | ✅ 规则映射 | LLM | **Python `direction-router.py`** |
| 设备翻译（焦段/景深/曝光） | ✅ 查表映射 | LLM | **Python `device-translator.py`** |
| 缓存查询/写入 | ✅ 精确操作 | LLM 读写 md | **SQLite + Python** |
| 位置缓存管理 | ✅ Key-Value | LLM "记忆" | **SQLite + Python** |

### 分界线 2：需要持久化 → 数据库

> **数据下次启动还需要、需要精确查找、需要计数 → SQLite。**

| 数据 | 特点 | 当前 | 产品 |
|------|------|------|------|
| 风格匹配缓存 | 频繁读、频繁写、需精确计数 | Markdown 表格 | **SQLite `style_cache` 表** |
| 技法缓存 | 同上 | Markdown 表格 | **SQLite `technique_cache` 表** |
| 设备能力档案 | 偶尔更新、频繁读取 | Markdown 文件 | **SQLite 或 YAML 配置文件** |
| 位置缓存 | GPS→地点，24h 过期 | 无持久化 | **SQLite `location_cache` 表** |
| 用户偏好 | 长期存储 | 无 | **SQLite `user_prefs` 表** |
| 摄影知识库 | 知识内容，非结构化数据 | Markdown ✅ | Markdown ✅（保留） |

### 分界线 3：需要理解或创造 → AI

> **需要"看懂"、"感受"、"判断"、"写作" → LLM。**

| 工作 | 为什么必须 AI | 不可替代性 |
|------|-------------|:--:|
| 视觉识别（豆包 API） | 需要"看懂"照片内容和光线特征 | 🔒 不可替代 |
| 风格搜索综合判断 | 需要从碎片搜索结果中"综合判断"什么适合 | 🔒 不可替代 |
| 审美主张引擎 | 需要"沉浸→洞察→生长创作方向"——是创造性行为 | 🔒 不可替代 |
| 方案生成（就这么拍） | 需要写出自然的口语化叙事——不是模板填空 | 🔒 不可替代 |
| 审美四维验证 | 需要主观判断"叙事完整性""调性统一度" | 🔒 不可替代 |
| 知识发现判断 | 需要判断"新风格是真发现还是噪音" | 🔒 不可替代 |
| 生图提示词写作 | 创作行为 | 🔒 不可替代 |

## 五、为什么 SQLite 不是 MySQL/PostgreSQL

- **零配置**：一个文件，不需要安装数据库服务器
- **零运维**：不需要备份策略、不需要连接池、不需要运维人员
- **Python 自带**：`import sqlite3` 不需要 `pip install`
- **适合单机**：你的产品是本地运行的 CLI/GUI 工具，不是 SaaS 多租户
- **够用**：缓存表最多几千行，SQLite 轻松处理百万行

**什么时候需要换数据库？** 当你有了后端服务器、多用户同时读写、需要主从复制时。在那之前，SQLite 是最正确的选择。

## 六、成本和收益预估

| 指标 | 当前（Skill 原型） | 第二阶段（代码化后） | 第三阶段（产品） |
|------|:--:|:--:|:--:|
| 单次调用 token | ~55-80K | ~30-40K | ~20-30K |
| 缓存查询可靠性 | ~80%（LLM 解析表格不可靠） | ~99.9%（SQL） | ~99.9% |
| 方向分配一致性 | ~70%（LLM 判断波动） | ~99.9%（规则引擎） | ~99.9% |
| 新增功能成本 | 改 Markdown | 改 Python + Markdown | 改代码 + 部署 |
| 用户感知延迟 | WebSearch + LLM 推理 | WebSearch + LLM（缓存命中时秒出） | 缓存命中秒出 + 后台 AI |

## 七、关键设计决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 缓存存储 | SQLite（不是 Markdown） | 精确查询、原子更新、不占 LLM token |
| 知识库 | Markdown（不是数据库） | 非结构化内容，AI 按需读取，人类也可读可改 |
| 方向分配 | Python 规则引擎（不是 LLM） | 确定性规则映射，不需要 AI 判断 |
| 审美主张 | LLM（不是代码） | 需要"沉浸""洞察""生长"——创造行为不可编程 |
| 方案生成 | LLM（不是模板） | 口语化叙事需要"语感"——模板做不到自然 |
| 数据库选型 | SQLite（不是 MySQL/PG） | 单机工具，零配置，Python 自带 |
