## 核心发现

共发现 **8 个设计级缺陷**、**7 个逻辑不自洽**、**5 个体验断层**，按严重程度排列。

## 🔴 设计级缺陷（会导致流程断裂或功能不可用）

### 1. "分屏逐屏展示"在终端中根本不存在

**位置**: `SKILL.md` 阶段 2/3 (L826-1049) | **严重度**: 致命

整个 v3 设计围绕"逐屏展示"——11 屏内容像刷短视频一样一次只看一张卡片：

```
第 1 屏：场景洞察 → 第 2 屏：🟢现在就拍 → 第 3 屏：🔥最出片 → ...
"用户在任何一屏选'就这个'→ 立即跳到阶段 3，后续卡片不展示。省 token"
```

**问题**：Claude Code 是终端文本界面，不存在"屏"的概念。AI 只能：
- 一次性输出所有内容
- 或者在每段输出后等待用户回复

"用户点'下一套'"意味着 AI 必须在输出方案 1 后**主动停止**，等用户说"下一套"再继续。这个机制依赖 AI 的自我中断，但 SKILL.md 没有定义中断协议——AI 不知道什么时候该停、什么时候该继续。实际操作中 AI 很可能一次性输出 4 套方案，使得"省 token"的设计前提完全失效。

**影响**：整个 v3 的"省 token"设计哲学建立在不可靠的基础上。实际使用时要么全部一次性输出（浪费 token），要么 AI 自行判断中断点（不可预测）。

---

### 2. 豆包 API 硬依赖——无降级路径

**位置**: `SKILL.md` L371-417 | **严重度**: 致命

```
⛔ 硬约束：必须使用豆包视觉 API 进行结构化识图。
禁止使用本地 Python 脚本（PIL/OpenCV/色彩统计）替代视觉模型。

⛔ 如果跳过此步骤直接用本地脚本分析 → 方案作废，回到 1A 重新识别。
```

如果出现以下任何情况，整个 skill 完全失效：
- 用户没有豆包 API key
- API 欠费/配额耗尽
- API 服务故障
- 网络问题

**没有降级路径。** 即使 `exif-extract.py` 已经提取了完整的 EXIF 数据（焦距、ISO、快门、GPS 等），这些数据在无视觉 API 的情况下完全无法被利用。

### 3. 知识缓存系统依赖 LLM 解析 Markdown 表格——本质上不可靠

**位置**: `style-router.md` §3.2-3.3 | **严重度**: 高

缓存命中分级系统（S/A/B/C）要求 LLM 做精确的数学计算：

```
扫描缓存表每一行 → 计算匹配度：
  光线：完全一致=2分，同大类=1.5分，可类比=1分，相反=0分
  题材：完全一致=1分，相近=0.5分，不同=0分
  情绪：高度一致=1.5分，部分一致=1分，不一致=0分

取最高分的那行：
  总分 ≥ 4.5 → S/A 级
  总分 3.0-4.4 → B 级
  总分 < 3.0 → C 级
```

**LLM 不擅长做这种精确的计分运算。** 同一个场景输入，不同轮次可能算出不同的分数，导致同一场景有时走 S 级（0 次 WebSearch），有时走 C 级（5-7 次 WebSearch）。缓存的"确定性加速"效果不可靠。

同样，Step 4 的缓存对比（"AI 推荐与缓存不一致→AI 优先，标记差异"）要求 LLM 准确判断两个风格描述是否"一致"——这是语义匹配问题，LLM 的语义匹配天然有模糊性。

### 4. 阶段 0 GPS 缺失时整个 v2.1 核心功能静默崩塌

**位置**: `SKILL.md` L153-154 | **严重度**: 高

```
本阶段为可选。若照片包含 GPS 数据，静默执行环境感知。
若照片无 GPS 数据，跳过本阶段。
```

但 v2.1 的核心升级——"位置感知上下文注入"——完全依赖 GPS 数据。没有 GPS 时：
- 0B 地点识别 → 跳过
- 0C 太阳位置 → 跳过
- 0D 天气查询 → 跳过（或严重降级）
- 0E 位置情报 7 路搜索 → 跳过
- 0F 时域调度 → 跳过

这意味着以下场景中，v2.1 的关键功能全部失效：
- 所有截图（无 EXIF）
- 社交媒体转发图片（EXIF 被剥离）
- 相机 RAW 文件未保留 GPS
- 用户在室内拍摄且无 GPS 信号

**v2.0 → v2.1 的核心卖点（位置感知）在大量实际使用场景中不生效。** 但用户不会知道——因为"全部静默，用户不可见中间结果"。

## 🟡 逻辑不自洽

### 5. 三个核心文件的"排除/标注"逻辑互相矛盾

三个路由文件对"是否排除"的原则不一致：

| 文件 | 原则 | 原话 |
|------|------|------|
| `style-router.md` §六 | **完全不排除**（仅安全红线） | "光线物理不完全匹配 → **诚实标注**，不排除" |
| `direction-selector.md` §三 | **大量排除** | "需要特定光方向但当前光不满足的 → **永远不会出现**在「现在就拍」" |
| `aesthetic-assertion.md` §Step 5 | **审美判断排除** | "排除不是因为'做不到'——是因为'不应该'" |

这三者说的是同一件事（什么风格进入推荐），但结论完全不同：
- style-router 说：光线不匹配 → 标注 🟡，不排除
- direction-selector 说：光线不匹配 → 不进入「现在就拍」
- aesthetic-assertion 说：审美冲突 → 排除

**在 pipeline 中，这三个判断有先后顺序——但 AI 没有收到如何协调三个矛盾指令的明确协议。** 可能出现的情况：style-router 热情推荐了一个光线不匹配但"可模拟 70%"的风格，direction-selector 在「现在就拍」中把它排除了，但 aesthetic-assertion 又可能因为"设备优势"把它拉回来。

### 6. 15 秒默认超时与信息密度根本矛盾

**位置**: `SKILL.md` L882, L981 | **严重度**: 中

```
如果用户在 15 秒内无操作 → 自动走 🟢 现在就拍
```

v3 设计是逐屏展示 4 张方向卡片（洞察 + 🟢 + 🔥 + ✨），每屏一张。如果每张自动展示 3-5 秒，4 张卡片展示完毕就已经 12-20 秒。用户刚看完最后一张卡片，还没来得及反应，系统就自动选了第一个。

**这与 SKILL.md 自己的表述自相矛盾**：
- "用户在任何一屏选'就这个'→ 立即跳到阶段 3"
- 但 15 秒倒计时是从哪个时刻开始计算的？如果是第一屏开始算，用户还在看第三屏时就已经超时了。

**更根本的问题**：Claude Code 没有"超时自动执行"机制。这个 15 秒默认行为是 AI 的自我约束指令，但 AI 无法精确感知时间流逝。

### 7. "预计算至少 2 种题材"与"省 token"直接矛盾

**位置**: `SKILL.md` L821 | **严重度**: 中

```
同时预计算至少 2 种题材的方向（默认题材 + 最可能的备选题材），切换时 0 延迟。
```

这意味着阶段 1 的整个 AI 引擎 pipeline（AI 搜索 + 诚实标注 + 缓存对比 + 审美主张）可能跑 2-3 遍。每次 run 包含 5-7 次 WebSearch。预计算 2 种题材 = 10-14 次 WebSearch。

**然后 SKILL.md 在阶段 3 说"方案 2-4 不生成（省 ~40% token）"。**

预计算造成的额外 token 消耗（10+ 次 WebSearch）远超所谓省下的 40% token（少生成 3 套方案的文字）。这是一个典型的"捡了芝麻丢了西瓜"的优化。

---

### 8. "光质修正表"的精度与天气数据的时效性脱节

**位置**: `SKILL.md` L222-232 | **严重度**: 中

```
硬光/顶光硬光 | 多云（云量20-70%） | 中硬光→软光 | 降低1-2级 | ...
```

这张表使用精确的云量百分比（20-70%）和光比数值（≤1:4）来做决策。但天气数据来源是 `wttr.in` 的免费 API——数据可能是几小时前的预报，且免费 API 的云量精度远达不到 20% 的区分度。

基于不精确的数据做精确决策 → 可能出现"根据天气数据判定为多云柔光→推荐森系→实际是大晴天硬光→用户按方案拍，效果很差"。

---

### 9. 脑洞大开的可行性百分比是 AI 虚构的

**位置**: `direction-selector.md` L365-368 | **严重度**: 中

```
"iphone_alternative": {
  "feasibility": "🟡 能做到 30%",
  "method": "等到傍晚天色暗下来，用手机闪光灯..."
}
```

"能做到 30%" 等百分比是 AI 在没有测量、没有基准、没有对比的情况下凭空生成的数字。用户可能看到 "30%" 后理解为精确的技术评估，实际上这是纯粹的猜测。

**更严重的是**：这些百分比在不同方案间不一致。今天的 AI 可能说"能做到 30%"，明天同样的场景可能说"能做到 50%"，用户会产生困惑。

### 10. 技法路由与风格路由的职责边界在极端情况下模糊

**位置**: `technique-router.md` §一 | **严重度**: 中

```
某些风格的辨识度恰恰来自特定技法：
- Lofi 直闪 → 属于风格定义的一部分——必须包含
- 微观微距 → 属于风格定义的一部分
```

如果风格路由匹配到了"Lofi 直闪"，同时技法路由也独立搜索到了"强制闪光灯"技法——这个技法算谁的？风格路由说"这是我的风格构成要件"，技法路由说"这是我搜索发现的技法"。

**如果同一个技法被两个路由同时命中，它会在方案中重复出现（一次来自风格配方，一次来自技法启发），或者在缓存中被重复注册。** 虽然 §一末尾有一条规则试图处理，但依赖 AI 在运行时正确判断归属——不可靠。

## 🟠 体验断层

### 11. "静默执行"掩盖了所有错误——用户看到空白等待

**位置**: `SKILL.md` 阶段 0-1 | **严重度**: 高

阶段 0 和阶段 1 全部标记为"静默执行，用户不可见中间结果"。这意味着：

- exiftool 未安装 → 静默失败，用户不知道
- 豆包 API 超时 → 静默重试，用户干等
- Nominatim 返回垃圾数据 → 静默忽略，整个位置感知降级
- WebSearch 全部返回无关内容 → AI 硬编方案，用户看不出区别

用户提交照片后，看到的是长时间的沉默。在 Claude Code 中，这意味着没有输出、没有进度提示、没有任何迹象表明系统在工作。用户可能会以为 skill 卡住了。

**建议**：至少显示一个进度提示——"正在分析你的照片..." → "正在查找最佳拍摄方案..."，而不是完全静默。

---

### 12. "题材切换"是假功能——实际无感知

**位置**: `SKILL.md` L977-979 | **严重度**: 中

```
用户点击题材切换标签 → 立即展示新题材的方向卡片（预计算，0 延迟）
不重新调用视觉 API，不重新分析场景
```

"预计算 2 种题材"意味着从用户上传照片到方向卡片出现，AI 已经为 2 种题材各跑了一遍完整的 AI 引擎 pipeline。用户看到的"切换"只是从预计算结果中选择另一套显示。

**但问题在于**：用户不知道哪些题材被预计算了。标签上写着"切到 🏞 环境"、"切到 ☕ 静物"——但如果用户想切换到未被预计算的题材（如街拍），系统需要从头跑 pipeline，此时"0 延迟"的承诺被打破。

---

### 13. 用户首次使用 vs 第 100 次使用——体验完全不同但没有说明

**位置**: `style-router.md` §3.3.4 | **严重度**: 中

```
| 使用量 | 缓存行数 | S/A 命中率 | C 命中率 | 平均 WebSearch |
| 初始（24 行）| 24 | ~5% | ~80% | ~6 次 |
| 成熟期 | ~500+ | ~50% | ~15% | ~1.5 次 |
```

**首次用户的体验**：80% 概率走 C 级（深度搜索），5-7 次 WebSearch + 3-4 次技法搜索 = **8-11 次 WebSearch**。响应时间长，成本高，体验差。

**成熟用户的体验**：50% 概率走 S 级（零搜索秒出），平均 1.5 次 WebSearch。响应快，成本低。

但用户看到的界面完全一样。首次用户不知道为什么有时候要等很久（深度搜索）、有时候秒出（S 级命中）。这种体验的不一致性没有被管理。

---

### 14. "自动知识沉淀"依赖 AI 编辑文件——可能悄悄损坏知识库

**位置**: `style-router.md` §五 | **严重度**: 中

```
方案生成完毕 →
  ├─ 检查方案中使用的风格匹配关系
  │   ├─ 在缓存表中？ → 验证计数 +1
  │   └─ 不在缓存表中？ → 🆕 自动注册
```

"验证计数 +1"意味着 AI 需要：
1. 定位缓存表中正确的行
2. 读取该行的验证计数
3. 将数字 +1
4. 用 Edit 工具精确替换

**如果一个步骤出错**：替换了错误的行、写入了错误的计数、格式不一致导致后续解析失败——缓存数据就被悄悄损坏了。没有校验步骤，没有回滚机制。随着使用次数增加，缓存表会逐渐积累格式错误和脏数据。

### 15. 方案差异化维度的"机械填表"风险（v3.2 试图解决但未根本解决）

**位置**: `SKILL.md` L1066-1074 | **严重度**: 低

```
| 维度 | 方案 1 | 方案 2 | 方案 3 | 方案 4 |
| 构图 | 三分法 | 前景虚化 | 留白构图 | 引导线/框架 |
| 景别 | 中景 | 近景/特写 | 远景 | 创意角度 |
```

v3.2 引入了技法路由来解决"方案差异化 = 维度的排列组合"问题。但技法路由仍然依赖 AI 搜索来获得灵感——如果搜索没返回好技法，AI 会退化为填表模式。**而技法缓存同样面临冷启动问题（初始只有 15 行）。**

## 🔵 架构观察

### 16. SKILL.md 1743 行——每次调用成本极高

`SKILL.md` 作为 skill 入口，每次 `/daipai` 都会全量加载到上下文。1743 行约等于 ~45K token。加上知识文件读取和 WebSearch，单次调用的 token 消耗预估：

| 场景 | SKILL.md | 知识文件 | WebSearch | 输出 | 合计估算 |
|------|:--:|:--:|:--:|:--:|:--:|
| S 级命中 | 45K | 5-10K | 0 | 2-3K | ~55K |
| C 级（首用） | 45K | 10-20K | 8-11 次 | 3-5K | ~80K+ |

这个成本对于一个"帮用户拍张照"的 skill 来说偏高。

---

### 17. 缺少失败恢复机制

整个 pipeline 没有定义任何错误恢复协议：

| 失败点 | 当前行为 | 应有行为 |
|--------|---------|---------|
| exiftool 未安装 | 静默跳过 | 告知用户 + 提供安装命令 |
| 豆包 API 故障 | 卡住/失败 | 降级到本地分析 + 告知限制 |
| Nominatim 超时 | 静默跳过 | 告知用户位置识别不可用 |
| WebSearch 全无结果 | AI 硬编 | 诚实告知 + 仅基于知识库推荐 |
| 方案审美验证 < 6 分 | 重新生成 | 限制重试次数（避免死循环） |

## 🎯 修复优先级建议

**P0 - 架构层面必须解决**:
1. 重新定义"分屏"——在终端中可行的交互模型（如：先出洞察+brief 选择提示，用户回复数字选择）
2. 增加豆包 API 的降级路径（EXIF-only 模式 + 本地知识库匹配）
3. 增加阶段 0-1 的进度提示（不能完全静默）

**P1 - 逻辑自洽**:
4. 统一三个文件的排除/标注原则，定义明确的协调协议
