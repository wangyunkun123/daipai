# 旅行记忆归档器 —— 产品思考

## 背景

在做「带拍」系列产品思考时，我们一直围绕一个假设展开：**用户想"拍得更好看"**。

于是有了隐形式方案相机（把摄影知识编译进相机行为）、高频场景矩阵（把场景分类做到极致）、男友拍照引导（帮不会拍照的人出片）。这些方向的共同点是——**给用户一件"更好的工具"**。

但当我们把视野从"拍照动作"放大到"照片的一生"，一个被忽视的真需求浮出水面：

> **用户不缺"拍得好看"，缺"拍完怎么办"。**

手机里躺着上万张照片、视频、截图、教程、票据，占了半个手机的内存，删了怕丢回忆，不删又天天提示空间不足，想找一张去年旅行时的票据翻半天翻不到。

**这不是"锦上添花"，这是"雪中送炭"。** 每个旅行的人都在经历，每次旅行都在发生，且没有任何一个产品解决过。

---

## 真需求 vs 伪需求

判断一个需求是不是真的，不要问"用户会不会觉得这个有用"，要问**"不用它的代价是什么"**。

| 判别维度 | 伪需求（修图/构图/审美工具） | 真需求（记忆资产归档） |
|---------|---------------------------|---------------------|
| 动机 | 锦上添花（更好看） | **消除负向焦虑**（空间焦虑 + 删除焦虑 + 找不到焦虑） |
| 频率 | 偶尔拍完才想用 | **每次旅行都必然发生**，年年发生 |
| 现状代价 | 不用也没有损失 | 不用就**持续被占空间、持续焦虑、持续找不到** |
| 反义词 | "好看" | "难受" |

**核心判别：伪需求的反面是"不做也没什么"，真需求的反面是"不做就很难受"。** 空间焦虑和删除焦虑是每个用 128G 手机的人都懂的情绪——这是刚需的信号，不是被创造出来的需求。

---

## 核心场景

用户原话（还原）：

> 每次旅行会记录一大堆照片、视频、截图、教程、票据啥的，放在相册里比较占空间，删除掉又感觉是珍贵的回忆，有没有什么好的办法。

一次普通的旅行，手机里会积累：

```
📷 照片     —— 2000+ 张（HEIC / Live Photo / Raw，存储大头）
🎬 视频     —— 几十段（Vlog、Live Photo 片段，占空间大户）
🖼 截图     —— 攻略截图、地图截图、餐厅推荐、朋友发的定位
📌 教程/攻略 —— 收藏的小红书笔记、网页、备忘录、PDF
🎫 票据     —— 机票、高铁票、门票、酒店订单、发票
💬 聊天资料  —— 微信里收到的行程单、合影
```

**它们属于同一次旅行，却散落在 5 个不同的地方。**

---

## 四大痛点

任何一个单独拎出来都是真需求，整合起来就是一个完整的机会：

### 1. 占空间
- 照片 + 视频占掉手机存储的大头，128G/256G 用户每年都在跟空间搏斗
- 这是持续的、每月都会复发的成本

### 2. 舍不得删（情绪资产）
- "删了可惜"——这些不是数据，是回忆
- 用户面对的是**空间焦虑 × 删除焦虑**的双向拉扯，比单独任何一种都更难受

### 3. 找不到
- 半年后想找"那家火锅店叫什么""当时那张门票的价格"，翻遍相册 + 截图 + 备忘录
- 现有检索是"按时间翻"，不是"按记忆找"

### 4. 散落
- 同一趟旅行的资料分散在相机、截图、备忘录、微信、邮件
- 回忆是**按"事件"组织**的，存储却是**按"类型"分散**的——这个错位就是痛点的根源

---

## 核心洞察

现有市场上的每一个产品，都只是"单一资产类型"的垂直工具：

| 现有产品 | 管什么 | 不管什么 |
|---------|-------|---------|
| Google Photos / 苹果相册 | 照片 + 视频 | 截图、票据、教程、聊天资料 |
| 百度网盘 / iCloud | 备份 | 不整理、不压缩、不结构化 |
| 寻隐 / 图智相册 | 照片检索 | 票据、教程、视频压缩、空间释放 |
| 航旅纵横 / 携程 | 机票酒店订单 | 照片、截图、攻略 |
| 随手记等记账 | 消费 | 要手动，不从票据自动提取 |

**没有产品把"一次旅行"当成一个完整的记忆单元。**

用户回忆的方式是"那次成都之行"，而不是"我那 2000 张照片"。但没有任何软件用"人生事件"作为组织单位来整合全部资产。

> **缺口不在"更聪明的相册"，在于"没有以事件为单位的记忆资产整合"。**

---

## 产品概念：一次旅行，一个档案

产品名暂定 **「旅行归档器」（Trip Archive）**。

核心价值主张：**一次旅行，一个档案，不占空间，随时可找回。**

工作流五步：

### ① 自动成档

AI 通过地理位置聚类 + 时间窗 + 照片拍摄规律，自动识别"这次旅行"（从出发到回家），并自动归拢该期间的所有资产：

- 📷 照片 / 🎬 视频（相机胶卷）
- 🖼 截图（攻略、地图、餐厅、定位）
- 🎫 票据（机票/高铁/门票/发票 → OCR 识别）
- 📌 收藏的笔记/链接（小红书收藏、备忘录）
- 💬 聊天里收到的资料（可选授权）

### ② 智能压缩（解决"占空间"，核心卖点）

```
连拍去重   → 同场景 N 张选 1 张最优，其余转低清归档
视频压缩   → 压到 1080p/720p 归档版，原片入云端
截图 OCR   → 转成文字后，截图本身可压缩
票据 OCR   → 转成结构化数据（日期/金额/地点/类型），原图可删

结果：一趟旅行从 30GB 压到 3-5GB
```

### ③ 结构化成"行程档案"

- **时间线**：Day 1 抵达 → Day 3 景点 → ……（按天自动分组）
- **分类页**：照片 / 视频 / 门票 / 攻略 / 花销
- **自动旅行日志**：每天精选 5 张 + 自动配文（地名、行程、票根拼贴）

### ④ 归档并释放空间

压缩 + 结构化完成后，原图一键"上云、删本地"，本地只留轻量版。

**释放几十 GB，但记忆完整保留，随时可下载原图。**

这是用户感知最强烈的一步——它不是"更漂亮"，是"手机突然不卡了、空间回来了、回忆还在"。

### ⑤ 随时检索 / 回顾 / 分享

- **自然语言检索**："找我在成都吃的那家火锅" → 返回照片 + 票根 + 攻略截图
- **一键回忆片**：照片 + 视频 + 票根拼贴成 1 分钟短片
- **纪念品**：生成电子相册 / 纸质书（把机票门票印进去，纪念感极强——这也是付费点）

---

## 为什么现在没人做

1. **能力栈深**：同时需要 相册理解 + OCR（票据/截图）+ 视频压缩 + 地理聚类 + 云端存储。单一团队很少全都有，而且每块都是深水区。

2. **巨头动机偏差**：Google / Apple 的商业逻辑是让用户**用他们的云备份**（增加存储收入）。做好"整理 + 主动压缩释放空间"反而与云存储商业利益部分冲突——所以他们停在"备份 + 回忆影片"，不碰"票据/截图/教程整合 + 主动压缩"。

3. **品类空白**：没有人用"一次人生事件"作为组织单位。所有产品都在"资产类型"维度上垂直，没有人在"事件"维度上整合。

---

## 技术可行性

### 能力复用（正好吃现有技术栈）

| 任务 | 技术 | 说明 |
|-----|------|-----|
| 连拍选优 / 视频关键帧 | 视觉（豆包 Lite） | 同场景去重选最优、视频压缩关键帧判定 |
| 票根 / 截图 OCR | 视觉（豆包 Lite） | 票据结构化为消费记录、截图转可检索文字 |
| 行程聚类决策 | 推理（DeepSeek Flash 关思考） | 地理位置 + 时间窗判定"这次旅行"的边界 |
| 归档文案 / 回忆片脚本 | 推理（DeepSeek Flash 关思考） | 自动旅行日志、回忆片旁白 |

### 架构原则

- **本地为主**：OCR、选片、压缩尽量端侧完成 → 快、省流量、隐私安全
- **云端精选**：原图/原片入云端，作为"随时可下载"的存档层
- **删除安全感机制（关键）**：任何"删本地"动作，先校验云端备份成功、给 30 天可恢复期。**没有这个机制，用户不敢用。**

### 性能底线

- 端侧选片/OCR 需在 iPhone 12（A14）及以上流畅运行
- 视频压缩用端侧 GPU/硬件编码器，避免长时间占用 CPU 发热

---

## 护城河

**数据复利**：用户的旅行档案越攒越多、越不可迁移——这是比"拍得更好看"深得多的壁垒。

- 2018 年的东京、2021 年的成都、2026 年的新疆——每一趟都被结构化、可检索、可回顾
- 换手机不丢、跨 iOS/Android 可访问
- 这是 Google Photos 也没做到的"结构化记忆"资产

---

## 风险与对策

| 风险 | 对策 |
|-----|------|
| 存储成本（原图/原片云端） | 按"归档空间"分层收费（免费 5GB，付费扩容）；AI 处理费另计 |
| 大厂跟进（Google Photos 可能做） | 靠"非照片资产（票据/截图/教程）整合 + 释放空间导向"切入——这是他们商业上不做、产品上懒得做的缝隙 |
| 用户信任（删本地 = 怕丢） | 可恢复机制 + 透明度（明确显示"释放了多少空间、删了什么、什么时候可恢复"） |
| 数据迁移成本（导入门槛） | 先支持系统相册/相簿一键导入，降低冷启动门槛 |

## MVP 建议

先做 iOS 单平台，只做一条链，验证核心假设：

```
┌────────────────────────────────────────────┐
│  MVP: 旅行归档闭环                          │
│                                            │
│  1. 旅行自动成档                            │
│     → 地理聚类 + 时间窗识别"这次旅行"        │
│     → 实现：豆包 Lite 场景理解 + 位置聚类     │
│                                            │
│  2. 连拍去重 + 视频压缩                     │
│     → 同场景选优 1 张，视频压到 1080p        │
│     → 实现：视觉模型选片 + 硬件编码器         │
│                                            │
│  3. 票据 OCR → 消费记录                     │
│     → 机票/门票/发票结构化                   │
│     → 实现：豆包 Lite OCR                   │
│                                            │
│  4. 一键归档 + 释放空间                     │
│     → 上云删本地 + 30 天可恢复 + 空间报告     │
│                                            │
│  5. 自然语言检索                           │
│     → "去年海边的合照" / "成都火锅店"        │
│                                            │
│  不做的（等验证后再加）：                    │
│  - 自动旅行日志文案                        │
│  - 回忆片生成                             │
│  - 纸质书/电子相册                          │
│  - 聊天资料整合（隐私重，放最后）            │
└────────────────────────────────────────────┘
```

**验证指标**：用户在第一次归档后，是否立刻感受到"空间回来了 + 记忆还在"，并主动归档第二趟旅行。

---

## 终极形态的想象

当"事件归档"被验证后，产品自然地从"旅行"扩展到"人生"：

- 一次旅行 → 一个档案
- 一次宝宝出生 → 一个档案（成长时间线 + 里程碑）
- 一次搬家 → 一个档案
- 一次创业 → 一个档案
- 一个人的人生 → 一部可检索、可回顾、可传承的**人生档案**

那时候它不再是一个"相册工具"，而是**一个人对自己生命的整理与叙事**——这是所有拍照产品的终点，也是没人到达过的地方。

> **拍得好看只解决当下，记得住才解决一生。**
